# ShadowClaw 设计文档

> 状态：设计定版（2026-10-21 与 li 逐项拍板），项目定名 ShadowClaw（li 的个人分身/影子，带 OpenClaw 式 agent 产品味）。定位：只给 li 自己用的个人 Agent，配齐他工作中的工具，目标是能像他一样思考和解决问题。与既有项目的关系：执行层以 muse-agent 为原型基础，评估层以 harness2-demo 的循环为原型。目标记录：goal_c7455ee51692。

## Step 1 · 总体架构：三层

```
┌─────────────────────────────────────────────┐
│ 评估层：自我迭代（攒批离线跑，只改驾驭层）      │
├─────────────────────────────────────────────┤
│ 驾驭层：原则 / 手册 / 记忆 / 工具 / 护栏 / 场景 │
├─────────────────────────────────────────────┤
│ 执行层：编排运行时（五种原语 + 规划者拼装）      │
└─────────────────────────────────────────────┘
```

- 执行层负责「把一次任务跑完」；驾驭层负责「按 li 的方式跑」；评估层负责「跑完之后变得更像 li」。
- 反思在执行层（任务内自检，改这一次的产出）；自我迭代在评估层（任务间改进，改驾驭层本身）。两层都有「改」，对象不同。

## Step 2 · 执行层

**职责**：统一的 agent 单元（模型 + 提示词 + 工具 + 记忆视图）之上，提供编排与底盘能力。

**五种编排原语**（代码实现的积木）：

1. 串行：上一步产出喂下一步
2. 路由：按任务类型与难度分给合适的执行者（便宜/强模型、专长 agent）
3. 并行：互不依赖的子任务同时跑，最后汇总
4. 反思：按验收标准自检，不合格就修
5. 委派：子任务整体交给子 agent，只收最终结果

**已拍板**：

- 编排方式 = 混合：原语是代码积木，规划者 agent 临场拼装；每次拼装决策进轨迹，评估层事后可评
- 状态传递 = 隔离副本 + 受控事实板：默认各 agent 带上下文快照独立干活、只回结果；任务级事实板只许写结论级结构化事实（已确认事实、产物索引、关键决策），合并归委派者，兄弟 agent 永不互写

**底盘能力（必备）**：结构化轨迹全量留档（评估层的输入）；失败处理（部分失败优先交部分结果）；并发上限/超时/重试；花费硬顶（超限停下问人）；长任务可中断可恢复；执行前审批挂钩点。

**默认值**：子代理深度上限 2。

## Step 3 · 驾驭层

**载体（已拍板）**：内容正本全部文件化（Markdown/YAML，独立 git 仓库，可看、可改、可回滚）；只有轨迹索引等机器数据进库。

```
harness/
  principles/    原则
  playbooks/     方法手册
  memory/        记忆
  tools/         工具配置与使用规矩
  guardrails/    护栏与审批策略
  scenarios/     场景配置
  skills/        技能库
```

**六个抽屉**：

1. **原则**：它是谁、遇事的默认态度。初稿（据 li 三个月共事观察提炼，待 li 审定）：先拆不变量再看细节；只认证据链、标注口径；拿不准明说、不伪造；错了当场改；给执行留否决权；表达分步、结论先行。
2. **方法手册**：每类活一份打法。li 的活类：维护项目、日志排障、修复、调研、建 Jira、技术文档。
3. **记忆**：关于 li 的事实/偏好/关系 + 工作知识（项目结构、历史结论）。召回默认：核心常驻注入，其余按需检索。
4. **工具配置**：先行接入 GitHub、Jira；其余按 li 提供的清单排队（待补：沟通、文档、日志监控、CI 等工具名）。
5. **护栏与审批**：沿用 li 的三级——只读自动干；写操作攒成一批一次确认；不可逆动作单独确认。
6. **场景配置**：每个场景启用哪些手册/工具/护栏。先只做工作场景。

**记忆写入权（已拍板，分级）**：

- 客观事实（li 明说的日期、项目名、决策结论）自动入
- 推断类（推断出的偏好、对人的评价、关系判断、原则级总结）必须 li 批准才落盘
- li 说过不记的永不自动入；删除即真删除

**手册冷启动（已拍板，B+C）**：B = 从 li 真实案例提炼 v1（排障记录、技术文档、Jira 单、合作记录），li 审改；理由与取舍由 li 口述补注脚。C = 上线后靠纠正回流持续生长。

## Step 4 · 评估层

**信号来源（按可信度）**：

1. li 的纠正与否决（真值）
2. 任务实际结果（修复是否解决、文档是否被采用、Jira 是否被退回）
3. li 的顺手反馈（满意/不满意）
4. 模型裁判（最弱，仅参考，用第 1 类信号持续校准）

**迭代回路**：攒批离线跑，不在干活时实时改。流程是：收集轨迹与纠正 → 提炼候选改动 → 在回归集上对照 → 过门才合入，进 git 可回滚。回归集用真实任务存档，多场景混合，分项卡门槛防互伤。每轮出一份短报告：改了什么、证据是什么、对照数据如何。

**硬边界**：只改驾驭层文件，永不改执行层代码；代码变更走正常开发（人提、人审、人合）。

**自主程度（已拍板，分级）**：教训级小改（手册补条目、场景参数微调）自动合入、留痕可回滚；原则层与护栏的改动必须 li 批准。

**节奏**：默认攒一周或攒满一批任务一轮，li 可手动触发。

## Step 5 · 层间接口

- 执行层 → 评估层：结构化轨迹契约（每步输入/输出/耗时/花费 + 编排拼装决策 + 最终产出）
- 驾驭层 → 执行层：注入点 = 每个 agent 单元的提示词、记忆视图、工具集、护栏挂钩
- 评估层 → 驾驭层：文件改动（git 提交形态），附证据与对照数据

## Step 6 · 待定与开发顺序建议

**待 li 补**：工作工具全清单（沟通/文档/日志监控/CI 等）；原则六条审定。

**待设计**：执行层底子复用 muse-agent 的程度（复用/重构/重写）；轨迹契约的字段级定义。

**开发顺序建议**：分四个阶段。阶段 0：冷启动材料提炼（手册 v1 + 原则定稿）。阶段 1：执行层最小回路（单 agent + 串行/委派 + 轨迹）。阶段 2：驾驭层 v1 + GitHub/Jira 接入。阶段 3：评估层回路，先只收信号与出报告，合入全审批，跑顺后切分级自主。
