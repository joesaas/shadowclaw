# ShadowClaw 评估层详细设计（含层间契约）

> 依据：docs/design.md 的评估层决策（信号可信度排序、离线攒批、只改驾驭层、分级自主）与驾驭层设计（锁定级文件）。本文同时定版三份层间契约（轨迹、注入、改动），均为字段级。

## Step 1 · 模块全景

```
evaluation/
  signals/      信号采集与存储
  attribution/  偏差归因（定位到驾驭层的哪一层、哪份文件）
  regression/   回归集管理
  proposer/     候选改动提炼
  contrast/     对照运行（候选版 vs 现行版）
  gate/         合入门与合入执行
  report/       迭代报告
```

主线一句话：**评估层只做三件事——收信号、提改动、守门**。它不参与任何一次任务的实时执行。

## Step 2 · 信号（signals/）

**信号 Signal（字段级）**：

- `id`、类型 `kind`、来源 `source`、关联轨迹 `trace_id`、关联任务、内容、时间
- `kind` 四类，可信度即权重序：`correction`（li 的纠正/否决，权重最高）> `outcome`（任务实际结果：修复是否生效、文档是否采用、Jira 是否退回）> `feedback`（顺手满意/不满意）> `judge`（模型裁判，最低，仅参考）
- `correction` 信号必须带 li 的原话引用；`outcome` 必须带可核查的结果引用（链接/状态），不收口头转述

**采集方式**：纠正在对话与影子对照环节随手记（结构化落库，不靠事后回忆）；结果在任务关闭时回填；裁判在对照运行时产生。信号只增不改，写错了追加一条更正信号。

## Step 3 · 归因（attribution/）

- 输入：一段时期的信号 + 对应轨迹（含 harness_version）。先按版本切分——只归因于同一驾驭版本产生的信号，跨版本不混算。
- 输出：偏差条目 {现象， 频次， 定位层（原则 / 手册 / 记忆 / 工具卡 / 护栏 / 场景）， 定位文件， 证据信号 id 列表}。
- 偏差分类固定枚举：方法错（手册步骤或原则问题）、事实错（记忆条目问题）、工具错（工具卡说明或风险级问题）、编排错（规划拼装问题，归因到执行层配置而非代码）、口味偏差（裁判与 li 标注不一致，进 Step 7 校准）。
- 定位不到层的偏差只记录、不提改动（不许猜着改）。

## Step 4 · 回归集（regression/）

- 构成：真实任务存档（输入 + 当时轨迹 + li 的标注结论），按场景分组；影子期（阶段 3）产出 v1，此后每轮迭代把新任务里的典型案例补进来。
- 纪律：**版本冻结**——集内案例一经入集不改标注；要改标注就新增版本并注明，老版本保留以便跨期可比。
- 指标（每场景分项）：任务成功率、被纠正率、单任务平均花费、平均耗时。对照与合入只认分项，不看总平均（防互伤被平均数掩盖）。

## Step 5 · 改动提炼（proposer/）

**候选改动 ChangeProposal（字段级，即改动契约）**：

- `id`、目标文件列表、具体 diff、改动等级 `class`
- `class` 三级：`lesson`（教训级：手册补条目、场景参数微调）/ `structural`（结构级：手册步骤重排、工具卡风险级调整、记忆条目修订）/ `locked`（锁定级：原则、护栏）
- 证据：信号 id 列表 + 归因条目引用（无证据不许提）
- 预期效果：写明预期改善哪个分项指标、可能伤到哪个（必填，不许只写好处）
- 状态：proposed / gated / merged / rejected

**提炼规则**：一个归因条目最多提一个改动方案；同一文件同时有多个候选时按证据强度排队，不并发改同一文件。

## Step 6 · 对照与合入门（contrast/ + gate/）

1. 候选版 = 现行 harness + 本轮全部候选改动的 diff，整体在回归集上重跑（用评估专用执行配置：同模型、同预算档）。
2. 门槛（全部分项判定）：任一场景的成功率或被纠正率**退步超过约定阈值（默认相对 5%）即整轮拒**；花费上升超过 20% 需在报告中单独说明并默认拒。
3. 分级合入：`lesson` 过门自动合入；`structural` 过门自动合入但报告重点标注；`locked` **无论对照结果如何都必须 li 批准**。
4. 合入形态：git 提交，提交信息含 ChangeProposal id 与证据信号 id；回滚 = revert 该提交，不做手术式反悔。
5. 被拒的改动连同对照数据进「负教训」存档，同类改动再次提炼时必须先回应上次被拒原因。

## Step 7 · 裁判校准

- 定期（每轮迭代时）抽查：judge 判定与 li 的 correction 信号在同一批任务上的一致率。
- 不一致案例汇总成校准材料：修订 judge 的判定提示词——这本身是一个 ChangeProposal，走同一道门，不许直接改。
- 一致率低于阈值（默认 70%）时，judge 信号在本轮权重降为零，只用前三类信号提改动。

## Step 8 · 报告（report/）

每轮迭代一份，固定结构：本轮信号量与构成 / 归因条目 / 候选改动与对照数据（分项前后值）/ 合入与拒绝清单（附理由）/ 负教训新增 / 裁判一致率。报告给 li 看，长度以一页为限。

## Step 9 · 三份层间契约汇总（字段级）

**轨迹契约（执行层 → 评估层）**：评估层消费的字段 = 轨迹头 {trace_id， 任务 id， 场景， harness_version， 起止时间， 结局} + Plan 全文 + 事件流（枚举见执行层设计 Step 5）+ 用量汇总 {token 入/出， 花费， 估算标记}。信号通过 trace_id 挂到轨迹上；没有 harness_version 的轨迹不入归因。

**注入契约（驾驭层 → 执行层）**：HarnessLoader 产出的 HarnessView = {场景 id， 原则全文， 命中手册全文 + 摘要集， memory_view（core + 检索条目）, 工具引用集（带风险级）, 审批策略对象， 预算顶， harness_version}。执行层只认 HarnessView，不直接读 harness/ 文件。

**改动契约（评估层 → 驾驭层）**：即 Step 5 的 ChangeProposal；合入后产生 git 提交，提交号回写到 Proposal 状态。锁定级另带 `approved_by: li` 字段，无此字段执行层加载时拒绝生效（双保险：流程拦一道，加载再拦一道）。

## Step 10 · 冷启动与节奏

- 评估层分两步上线：先只收信号、出影子报告（阶段 3），回归集 v1 就绪后才开提改动（阶段 4）。没有回归集时禁止任何自动合入。
- 节奏：默认每周一轮或攒满 20 条 correction 信号提前触发；li 可手动喊停某一轮或整体暂停评估层，暂停不影响执行层干活。
