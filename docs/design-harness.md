# ShadowClaw 驾驭层详细设计

> 依据：docs/design.md 的驾驭层决策（文件为正本、六抽屉、记忆写入分级、手册 B+C 冷启动、护栏三级）与执行层设计（UnitSpec 注入点、审批策略来源）。粒度同执行层：照此可直接写代码。

## Step 1 · 目录与格式总则

```
harness/
  principles/   principles.md（正文）
  playbooks/    <活类>.md：troubleshooting / research / tech-docs / jira
  memory/       core.md（常驻）+ facts/ people/ projects/ decisions/ + proposals/（待批队列）
  tools/        <工具>.yaml（一工具一卡）
  guardrails/   policy.yaml（审批矩阵 + 预算顶 + 红线）
  scenarios/    <场景>.yaml（一场景一文件）
  skills/       <名>/SKILL.md
```

- 格式分工：**人读的正文用 Markdown，机器读的元数据用 YAML**（独立文件或 frontmatter），不混杂。
- 整个 harness/ 就是驾驭层的全部正本，进 git；每次改动是一个提交，提交信息带证据出处（评估层合入时强制，见评估层设计）。
- 加载时做全量校验：引用不存在、格式不对，在启动时报错，不带病跑到任务中途。

## Step 2 · 六个抽屉逐个定

**1. 原则 principles.md**
- 结构：身份（它是谁、服务谁）/ 决策原则（每条 = 原则 + 适用说明 + 一个反例）/ 表达规范。
- 注入：**永远全量注入**，位于每个单元 instruction 的最前面，不参与检索、不裁剪。
- 变更等级：锁定级——评估层只能提议，li 批准才合入。

**2. 方法手册 playbooks/<活类>.md**
- 结构：适用场景（触发条件）/ 步骤（有序）/ 核对点（每步干完怎么验）/ 常见坑 / 输出规范 / 注脚（为什么这样做，li 口述的取舍）。
- frontmatter：{活类， 版本， 更新时间， 来源：案例提炼 / 手工}。
- 注入：规划者只看各手册的摘要（选路用）；执行单元拿命中手册的全文。

**3. 记忆 memory/**
- 分层：core.md 常驻（身份、当前项目、关键关系摘要，体积上限约 2k token，超了要先压缩再写入）；长期按类分文件（facts / people / projects / decisions），每条 = {陈述， 来源， 日期， 状态}。
- 检索：v1 用关键词 + 索引文件；向量检索留接口、后置（见待确认）。
- 注入：core 全量 + 按任务检索到的条目，组成单元的 memory_view。

**4. 工具卡 tools/<工具>.yaml**
- 字段：{名称， 接入方式（MCP 服务引用 / 函数工具）， 凭证引用（只写连接器名，永不写密钥）， 操作风险分级（每个操作标 read / write / irreversible）， 使用说明（何时用、已知的坑）}。
- 工具能不能被某个场景用、用到什么风险级，由场景与护栏决定，不由工具卡自己决定。

**5. 护栏 guardrails/policy.yaml**
- 审批矩阵：操作风险级 × 场景 → 自动 / 攒批确认 / 单独确认 / 禁止。矩阵之外一律 fail-closed 按「先问」。
- 预算顶：每场景单任务花费上限（执行层账本读取）。
- 红线：永不执行的动作清单（独立于矩阵，任何场景不可放宽）。
- 变更等级：锁定级——同原则，li 批准才合入。

**6. 场景 scenarios/<场景>.yaml**
- 字段：{名称， 覆盖活类， 启用的手册， 启用的工具及风险上限， 护栏档位， 记忆范围， 默认模型路由， 预算顶}。
- 场景是运行时组装驾驭视图的**唯一入口**：给一个任务先定场景，其余五件都经场景装配，不许绕过场景零散拼凑。

## Step 3 · 加载与注入机制

**加载器 HarnessLoader**：任务启动时按场景组装一份 HarnessView：

1. 读场景文件，解析出启用的五件清单
2. 原则全量载入；手册按活类命中；记忆 = core + 检索结果；工具卡按启用清单过滤；护栏 = 全局 policy 与场景档位合并（**从严不从宽**：冲突时取更严的一档）
3. 产出执行层要的注入物：UnitSpec 的 instruction 片段、memory_view 内容、工具引用集、审批策略对象、预算顶
4. **把 harness 的 git 提交号打进轨迹**（harness_version）：评估层归因的前提——哪条轨迹是哪一版驾驭层跑出来的，必须可查

## Step 4 · 记忆写入流程（分级落到机制）

1. 任务或对话产生候选记忆 → **分类器**判定类别：事实 / 推断 / 禁区。分类先用规则，拿不准的一律归推断（宁可多问，不可错放）。
2. **事实**：直接写入对应文件，带来源与日期；同时记一条 memory changelog（谁、何时、写了什么），可审计。
3. **推断**：进 memory/proposals/ 待批队列，不进长期记忆、不参与注入。li 攒批处理（本地阶段在 adk web 期顺手批；上 EC2 后走 Telegram）：批准 → 移入长期并标 li-approved；驳回 → 删除，并留一条驳回记录给评估层校准分类器。
4. **禁区**（li 说过不记的类别）：当场丢弃，不落任何文件。
5. **冲突**：新事实与旧条目冲突时，旧条目标记 superseded 并保留历史，不静默覆盖。
6. **删除**：li 要求遗忘 → 真删条目并清理索引与 changelog 中的派生引用。

## Step 5 · 冷启动（阶段 0 的具体做法）

- 材料：li 的既有记忆文件与人物索引、已交付的技术文档、本地工作记录、合作对话记录。
- 提炼流程：按活类聚类案例 → 抽步骤与核对点 → **每条手册条目标注证据出处**（出自哪个案例）→ li 审（删 / 改 / 补注脚）。
- 记忆种子：从既有记忆蒸馏，事实类直入；凡属推断类的，汇总成一份清单请 li 一次性审完再入。
- 原则定稿：六条初稿逐条过 li——保留、改写、删除、补充，当场定版 v1。

## Step 6 · 与评估层的接口

- 评估层只能改 harness/ 内的文件，且以 git 提交形态交付（见评估层设计的改动契约）。
- 锁定级文件（principles、guardrails）在提交元数据里带 requires_approval 标记，执行层加载时校验批准状态，未批准的锁定级改动不生效。

## Step 7 · 待确认（li）

1. harness/ 放主仓子目录起步（将来可拆独立仓）——推荐如此，运维最简。
2. 记忆检索 v1 只用关键词 + 索引，向量后置——可否。
3. 待批队列 v1 就用文件 + 人工处理，不做专门审批界面——可否。
