# ShadowClaw 技术选型定版

> 状态：2026-10-21 定版（与 li 逐项拍板）。选型标尺来自设计定版（docs/design.md）提炼的执行层十项硬需求：单元可注入、五原语齐备、规划者可临场拼装、状态语义自有（快照/隔离/事实板）、轨迹全量结构化、审批挂钩、预算与失败控制、中断可恢复、多模型、子代理生命周期可控。

## 选型结论

| 项 | 结论 | 一句理由 |
|---|---|---|
| 语言 | Python | ADK 主战场与既有实测经验都在 Python |
| 执行层底座 | Google ADK | 单元、委派、审批、多模型原生且已实测；短板（动态拼装、状态语义）用一层薄封装补 |
| 模型接入 | OpenRouter 为主通道（经 LiteLlm），接入层留薄封装 | 换模型只改配置；key 已配；不绑单一厂商 |
| 工具接入协议 | MCP 优先，无 MCP 的用函数工具自封 | ADK 原生支持 MCP；GitHub、Jira 都有官方 MCP |
| 存储 | 驾驭层文件为正本；轨迹与索引用 SQLite | 单用户量级足够，不预支复杂度 |
| 部署 | 本地电脑为第一落点；保持可迁移，后续部署 AWS EC2 | li 的分身住 li 的地盘；不写死本地路径与环境 |
| 渠道 | 本地用 `adk web` 的 UI 交互调试；上 EC2 后接 Telegram | adk web 是 ADK 自带开发 UI，影子期对照产出也够用；Telegram 是 li 的日常渠道 |
| 工程结构 | 单仓按三层分包：`execution/`、`harness/`、`evaluation/` + 入口应用 | 与三层架构一一对应 |

## 底座选型的取舍记录

- **落选：在 muse-agent 上全自研**。十项需求全能贴身实现，但五原语、轨迹、恢复大多要从零建，工时会被执行层轮子吃掉，拖慢驾驭层与评估层——本项目的护城河不在执行层。
- **落选：LangGraph**。状态图与检查点最强（恢复、介入原生），但世界观是共享状态，与已拍板的「隔离副本」语义相冲；且 agent 单元抽象要自搭，省不了多少工，还要新学一整套框架。（按公开资料评估，未在本环境实测。）
- **选中 ADK 的已知短板与对策**：编排偏静态 → 在其上加一层编排封装，规划者拼装出子代理树/workflow 再交给 ADK 跑；session 事件只追加 → 上下文类操作用「镜像→处理→轮换新 session」（muse-agent-adk 已验证此法）；版本年轻 → 锁版本，升级走回归集验收。

## 部署形态备注

- 本地阶段：`adk web` 启动，浏览器 UI 交互；进程随用随起，不做常驻。
- EC2 阶段：常驻服务（systemd），渠道换 Telegram bot；驾驭层文件与 SQLite 随代码一并迁移，路径全部走配置。
