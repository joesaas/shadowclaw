# 方法手册 · 排障篇

> 阶段 0 草稿，待 li 审定；来源：当前 agent 运行历史中的真实案例。

## 适用场景

出现以下任一情况时用这份手册：

- 线上服务行为与预期不符（功能不生效、状态不对、间歇失败）
- 构建、部署、推送、上传等工程链路报错或「报成功但没生效」
- 工具、脚本、自动化链路（hook、cron、daemon）静默失效或部分失效
- 第三方接口返回异常（超时、403、证书错误），且分不清是对方、环境还是自己的问题

不适用：纯功能开发（无故障现象）、需求与设计讨论。

## 步骤

### 1. 接手定界

先把问题说清楚再动手：现象是什么、影响谁/什么、什么条件下出现（必现还是偶发）。然后**先查自家记录**（长期记忆、`AGENTS.md`、既往案例）有没有同类问题与已定结论——很多「新问题」是已知边界或已记录的怪癖。

- **核对点**：能一句话说清「什么坏了、谁受影响、何时出现」；既有记录已检索，并注明命中了哪条或未命中。

### 2. 固定一手证据

直读报错原文、日志、状态接口的原始输出，并标注证据的时间与来源。不拿转述、二手截图、自己的记忆当证据；二手材料只能当线索。

- **核对点**：手上有原始输出；能指出失败发生在哪一段链条上（本机 / 代理与出口 / 对方服务），还指不出就继续取证，不进入猜测。

### 3. 分层排除、单变量探针

按层逐层排除：配置 → 凭证 → 版本与运行时 → 网络与出口 → 代码逻辑 → 权限边界。一次只动一个变量。用最小探针换路径直测来区分环境与代码：同一端点换工具直调、合成数据 dry-run、只读探针先行、从别的目录/身份复现。

- **核对点**：每一层被排除都有一条探针证据支撑，结论里不出现无证据的「应该是」。

### 4. 识破假信号

成功回执、状态字段、截图都可能说谎。写入类操作必须**回读核验**：文件真在盘上（大小、章节对得上）、远端与本地哈希一致、线上状态字段真的变了。证据互相冲突时，以确定性证据（字节、哈希、直读）为准，截图与转述降级为参考。

- **核对点**：关键结论至少有一条独立于执行动作本身的核验证据。

### 5. 定根因并分级

根因必须有证据链闭环才许下结论。结论分三档写：**已证实**（证据闭环）/ **推断**（证据指向但未闭环）/ **未证实**（查不到）。查不到就写「未知」——不可见不等于异常。官方文档与官方字段也要过一致性检查，自相矛盾时以可复算的数据为准，并标注哪项不予采信。

- **核对点**：每条结论都能指回具体证据；未证实项单列，不混进结论句。

### 6. 修复 + 原路复验

修复后沿**原失败路径**端到端复验一遍，不只验修复点本身。外部写操作先在本地攒齐、验完，打包成最少批次一次推完；写操作返回异常或结果未知时，**先核落点实际状态，再决定重做范围**，不整轮盲目重来。

- **核对点**：原失败场景实测通过；若只能验到局部，明说只验到哪一层、端到端未验。

### 7. 沉淀

把根因、修法、环境怪癖连同维护注意事项（如「某补丁会被官方 upgrade 覆盖」）写回 `AGENTS.md` / 记忆，并回读确认落盘——让下一次同类问题在第 1 步就能命中。

- **核对点**：记录在盘上且可检索；不是只写进了当次对话。

## 常见坑

1. **配置写了，进程没读到**——案例：DocReader 鉴权闭环（2026-10-12）：鉴权代码已推送、Key 也设了，但服务原本不读 `.env`，Key 进不了运行进程，线上 `auth.required` 一直为 false。最后靠公网探针定位（无 Key DELETE 应回 401 却回 404），给服务加启动加载 `.env` 后才闭环。教训：配置问题先验「进程实际读到了什么」，用外部探针验生效，不看代码改没改。
2. **工具报成功，文件没落盘**——案例：收录清单写入假成功（2026-10-12）：一次 write 回执报告写入 15,683 字节成功，全盘查找文件实际不存在，最终改用分段写入并逐段核验。教训：大文件写入后必须回读核验（大小、章节完整性），不轻信单次回执。
3. **表象是「消息丢了」，根因是一个参数类型**——案例：Telegram 自动回复 hook 失效（2026-10-07）：消息已被 hook 取走、水位已推进，但脚本把 `log()` 的 fields 传成 JSON 数组（运行时要求对象），在 `set -e` 下死在唤醒 worker 之前；而该链路是破坏性读取，消息消费即不可回取。教训：链路型系统按段定位，不要盯着表象层；破坏性读取的环节，消费前先想好保全与回放。答复与修复建议要写到可执行粒度：点名出错的那一步与参数，并给出具体改法（如把 log() 的 fields 由数组改为对象包裹 {count, messages}），不只说「参数类型不对」。
4. **报错栈崩在工具自己身上，先查环境版本**——案例：data-pipeline 在 EC2 首构建失败（2026-10-20）：TypeScript 编译器自身崩在 `??` 语法，根因是服务器 Node 版本低于 14，而项目要求 Node ≥ 22，非代码问题。修复除了升级版本，还加了 prebuild 版本检查，让下次直接报人话错误而不是解析栈。教训：先看报错崩在哪一层；环境前置条件（版本）先核对，再怀疑代码。
5. **同类操作两次 403，是能力边界不是 bug**——案例：GitHub App 权限边界（2026-10-14）：`create_repository` 与 `fork_repository` 均返回 403 `Resource not accessible by integration`——该 App 本就无建仓/fork 权限。教训：同类 403 先查能力边界，不要在调用层反复重试；改走可行路线（人工建仓后推送），并把边界写进工具备忘。
6. **验证证据本身会骗人**——案例：muse-design-site 截图串图事件（2026-10-16）：验收截图里出现页面上根本不存在的层名，重拍还返回同一张错图（文件哈希相同）；最终以 curl 直读线上文件与本地逐字节一致定案。教训：截图可能被缓存误导或串图；证据冲突时以哈希、grep、直读为准，截图核验要带缓存绕过。
7. **从产物回抽的「源」是脏的**——案例：answer-me-with-html 上传源污染（2026-10-16）：首次上传用了从渲染页内嵌 `#am-source` 回抽的「源稿」，抽取物混入页面自身脚本，正文膨胀十几倍；校验发现后用干净原稿重渲、原地替换。教训：上传与重渲一律用干净原稿，禁止从产物回抽源；交付前校验要查体积与结构异常。
8. **写操作报异常 ≠ 没落盘，也 ≠ 已落盘**——案例：设计站推送中途 invalid session（2026-10-16）：一批 push_files 界面显示 approved、实际报 MCP 400 未落盘。先以哈希核对确认该批未落，只重推这一批，其余不重来。教训：结果未知时先查实际状态再定重做范围，不整轮重推。
9. **客户端挂死，不等于对方服务挂了**——案例：Bankr 登录发码超时（2026-10-09）：CLI 在沙箱里两次挂满约 300 秒超时，但 curl 用等价参数直调同一 Privy 接口 6.4 秒成功——问题出在 CLI 在此环境的发码请求路径，不是服务端。教训：同端点换一条路径直测，能立刻分清责任段；另注意：此案根因未完全钉死，只定位到「CLI 发码路径」，汇报时按未钉死如实标注。
10. **日志写了 starting，进程其实没活**——案例：snowagent-a2a daemon 静默死亡（2026-10-08 起）：日志最后一
条停在 `daemon starting`、之后零输出，实查无进程存活，任务实际无人盯守多日。教训：判活要查进程存不存在 + 日志时间戳新不新，不能只看「曾经启动过」。
11. **官方字段也会自相矛盾**——案例：WBETH 年化口径处理（2026-10-12）：Binance 官方 `annualPercentageRate` 字段与其自家文档示例内部不一致，不予采信，改由汇率窗口增速反推年化，并加守卫（窗口 <7 天、有效点 <2、推出值超出 [0,20]% 即记失败不发数）。教训：官方口径也要验一致性；能复算的数据优先于字段直读，采信与不采信都要标注。
12. **证书报错，先怀疑出口与信任根**——案例：onchainos CLI 的 UnknownIssuer（工具备忘，`AGENTS.md`）：沙箱出口有 TLS 中间人代理，官方预编译二进制只信任 webpki 根证书，必然报错；最终从源码重编、改用系统原生根证书并把代理 CA 追加进系统证书库才通。教训：TLS 错误先分清是对方证书问题还是本方信任根/出口问题；这类修复必须连同维护注意事项一起沉淀（官方 upgrade 会覆盖补丁，需重打）。

## 输出规范

向 li 汇报排障结论时，按四段分开写，不许混：

1. **结论**：一句话先行——已修复 / 未修复 / 仍未知，以及根因是什么（只写已证实档）。
2. **证据**：支撑结论的关键证据，列原始出处（日志片段、状态字段、哈希、探针结果），可核查。
3. **未证实项**：推断与未知单列，写明卡在哪、缺什么证据；不把推断写进结论句。
4. **影响与残留**：修了什么、没修什么、剩余风险与待办（如补丁会被升级覆盖、端到端尚未复验）。

失败或没查清时同样如实报：做了什么、卡在哪、下一步需要什么。不报「应该好了」，不拿局部通过冒充端到端通过。

## 注脚

本手册的取舍——先证据后结论、宁可报未知不报假确定、修复必须原路复验、外部写操作攒批一次推完——均提炼自上列案例中 li 的实际验收口径；li 的口述取舍待审定时补充。

## 缺口标注

- 本手册只含**方法论**：全部案例出自当前 agent 的运行环境（沙箱 VM、连接器与凭证链、GitHub App、构建与部署链路）。
- 以下内容**不在本材料内，手册一字未填**：li 公司内系统的具体知识——内部服务拓扑与日志位置、Jira 等内部系统的实例与用法、公司网络与权限体系、各内部系统已知的常见故障模式与工具怪癖。
- 补法：待阶段 2 接入 Jira 等公司工具、或 li 投喂内部排障案例后，按本手册同样格式（每条坑对应真实案例、标注出处）增补「公司内系统」部分，另行送 li 审定。在此之前，遇到公司内系统问题只套用本手册的方法步骤，系统知识部分如实报缺，不拿推测填。
