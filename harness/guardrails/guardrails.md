## 策略矩阵（机器读）

审批按**操作风险级**分三级，矩阵之外一律 fail-closed 按「先问」：

```yaml
approval_matrix:
  read: allow               # 一级·只读：自动放行，不打扰
  write: ask_batch          # 二级·写操作：攒批，一次确认（见下方落地说明）
  irreversible: ask_separate  # 三级·不可逆：单独确认，不许搭车批量
  forbidden: deny           # 红线：禁止，任何场景不可放宽
budget_caps:
  default_task_usd: 5.0     # 单任务花费硬顶，计划预算不得超过（执行层账本读取）
red_lines:
  - 删除仓库、强制推送改写已发布历史等破坏性 Git 操作
  - 把凭据明文写进任何文件、输出或轨迹
  - 替 li 执行金融交易（只建议不代投）
  - 把 li 说过不记的内容写入任何记忆文件
```

落地说明（阶段 2）：

- `ask_batch` 的攒批语义本阶段先以 **ASK** 落地——写步骤执行前过审批挂钩，无人值守时 ASK 等同 DENY 并落轨迹；真正的批处理引擎（攒齐多步一次弹）后置，不在本阶段建。
- `ask_separate` 同样落为 ASK，但策略对象上带「须单独确认」标记：将来有人值守确认时，不可与其它写操作合并放行。
- 场景可在自己的档位里收紧（合并从严），不可放宽本矩阵与红线。

## 人读说明

三级策略对应 li 的确认门哲学——给机器执行力，给人留否决权，而不事事请示：

1. **只读自动干**：查仓库、看 issue、读日志这类不改变任何状态的动作，直接做完再汇报，不许拿只读动作来烦人。
2. **写操作攒批一次确认**：会改状态的动作（建 issue、改文件、推送）先在本地攒齐、想清楚，一次性拿给 li 确认，不许一轮轮弹。
3. **不可逆单独确认**：删、合并、发布这类撤不回的动作，每次单独确认，永远不搭车；红线动作则根本不做，li 本人在场明确要求时也先复述风险再定。
